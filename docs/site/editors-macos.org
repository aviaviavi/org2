#+TITLE: OpenOrg for macOS
#+SUBTITLE: A native workspace for local notes, planning, meetings, and agent work.

OpenOrg brings an ordinary folder of Org and Org2 files into one Mac app. Your files remain the source of truth, so you can also read, edit, sync, or version them with tools you already use.

* Start with an agent and today's note

On first launch, OpenOrg creates a plain-text workspace automatically and asks you to connect an agent already available on your Mac. Choose local Codex, local Claude Code, or an OpenClaw Gateway you already run. You can also continue without AI; OpenOrg does not require an account or agent.

After setup, Home opens immediately with a chat box and today's daily note side by side. Ask a question, write in the note, or do both. New notes use =.org=; existing =.org2= files remain fully supported and are not renamed. The initial workspace lives in a normal folder that you can move or rename. Use *OpenOrg → Settings… → Workspace* to update its portable name and kind, reveal it in Finder, or open a different corpus.

If you already keep notes in another folder, choose it from the workspace options during setup or mount it later from the corpus switcher. OpenOrg derives its views without moving your source of truth into a private database.

Global capture works anywhere on your Mac while OpenOrg is running. Press =Cmd-Ctrl-Return= to add a note or task to today's daily note, including dates, tags, links, files, or images.

OpenOrg stores daily notes in the corpus's =daily/= zone by default. Set =roam.dailiesDir= in =org2.json= to a valid absolute path or a directory relative to the corpus root to use a different location; missing or invalid values fall back to =daily/= rather than the corpus root.

* The workspace

- *Agenda* :: see scheduled work and deadlines across one or all open corpora. Filter by date, assignee, status, priority, topic, or text; mark items done, reschedule them, change priority, or open the source note.
- *Files* :: expand the cached corpus file tree directly in the sidebar, or use the full tree and search surface for Org, Org2, Markdown, CSV, and generated workspace files.
- *Agent Work* :: follow delegated runs, inspect outputs and citations, and handle decisions that need you.
- *Meetings* :: record or import audio and keep transcripts, summaries, decisions, and follow-ups together.
- *Sources* :: connect supported external sources such as Slack and Notion, run a sync, or control its schedule.
- *Skills* :: inspect workspace-authored agent procedures, open their =SKILL.md= source, create a new skill, or move one to the Trash.
- *AI Chat* :: talk with any configured local, remote, hosted, or self-hosted destination using selected workspace context.
- *Search and Quick Open* :: find text, tasks, files, people, projects, meetings, agent work, and chat threads without remembering where they live.

You can open several corpora and switch between them from the sidebar. Agenda and Search can read across all mounted corpora, while writes stay scoped to the active corpus.

Use tabs to keep several documents or workspace views open without mixing their navigation history, selected surface, surface mode, row selection, or two-pane layout. An Agenda tab therefore returns to Agenda, while an Agent Work or Skills tab returns to its own view and selection. Press =Cmd-T= for a new tab and =Cmd-Shift-[= or =Cmd-Shift-]= for the previous or next tab. Drag tabs to reorder them, or right-click one to duplicate, move, close, or close the other tabs.

Open *Skills* from the sidebar or press =Cmd-Shift-K=. Skills are ordinary =SKILL.md= files under =.agents/skills/=. Select a workspace-authored skill to edit it in the normal document pane, use *New Skill* for a safe starter file, and use the row menu to reveal it or move its whole folder to the Trash. Invalid skill files remain visible with a repair message instead of disappearing from the manager.

OpenOrg supplies its core Org2 operating guidance ambiently to every AI chat, so the reserved =org2= infrastructure skill is not shown as a user workflow or slash command. Its corpus copy remains available to external skill-aware agents. The Skills surface is for additional procedures authored for this workspace.

* Write and read

#+begin_export html
<figure class="org2-section-shot"><img src="assets/screenshots/macos-workspace-files.png" alt="OpenOrg Files view showing an Org2 note in the detail pane" loading="lazy" /><figcaption>Read a rendered document or edit the plain-text source.</figcaption></figure>
#+end_export

OpenOrg offers two views of the same document:

- *Read* renders headings, links, properties, tables, citations, media, source blocks, and other Org structure.
- *Edit Source* provides a native macOS text editor with syntax highlighting, folding, diagnostics, list continuation, TODO and planning commands, link insertion, undo, and safe saving.

An optional split view keeps source and rendered preview visible together. Rendered tables can be filtered, sorted, and resized without changing the source. CSV files open in an editable table with a raw-text fallback.

Trusted Org2 plugins can add renderers for source-block languages. The shared
CLI HTML runtime powers both read mode and source preview, so the same plugin
also works in =org2 export html= without a separate Mac extension or app
rebuild. Renderer UI runs in a sandboxed, opaque-origin frame. See
[[file:tooling-reference.org::*Plugins][Tooling reference → Plugins]].

OpenOrg can export an ordinary document or selected subtree as a clean PDF. Document PDFs preserve styled headings and content while omitting heading stars, outline guides and their indentation, disclosure arrows, property drawers, and interactive controls such as Ask AI. It can also preview slide decks and export presentation PDFs. Publication uses a disclosure-safe copy that removes private workspace metadata and unresolved local references from the shared output.

* Publish a document

Open an Org or Org2 document, open its document menu, and choose *Publish Document…*. The same sheet also opens from =/publish document= in AI Chat. Choose the entire document or the subtree at the current reading/editing position, then inspect the disclosure preview before publishing.

The publish sheet separates the *destination* from the *format*:

- *Local Link* can serve a read-only *Web page*, fixed-layout *PDF*, or compiled *Beamer slides (PDF)*. Web pages use the same fluid, bounded document layout as OpenOrg's reader; long text wraps, charts shrink with the viewport, and wide tables scroll inside the page instead of widening it. The destination creates a high-entropy secret URL from the Mac and persists its sealed artifact locally. Publishing the same document or subtree and format again updates that URL in place, including links created before stable republishing was introduced. Devices must be able to reach the Mac on the local or private network. OpenOrg must be running for a link to be reachable, and active links resume at the same URL after OpenOrg relaunches. The initial server uses unencrypted HTTP, so use it only on a network you trust. Open *Settings → Sharing* to see every source file and format currently hosted, open or copy a link, stop one, or stop all of them.
- *Google Drive* can create an editable *Google Doc*, *Google Slides* deck, or *Google Sheets* workbook, or upload a fixed-layout *PDF*. Slides use the selected content's slide headings. Sheets create one tab per Org table and refuse a selection with no tables. The optional folder ID selects a Drive folder; otherwise Google places the file in the connected account's default location. After the first successful publish, OpenOrg saves that format's Drive file ID, link, guarded version, and publish time in the selected document or subtree property drawer. The green *Google Drive* badge beside the document title reopens or copies saved artifacts, and publishing the same scope and format again updates the linked file instead of creating a duplicate. OAuth credentials remain in macOS Keychain and are never written into the source. Google Drive owns sharing and identity. *Connect Google Drive* opens Google's consent page in the default browser using the desktop loopback and PKCE flow, requests only the per-file =drive.file= scope, and keeps the refresh credential in macOS Keychain.

Web pages and fixed-layout PDFs embed deterministic =chart= and =plot= visualizations. A chart's source table must be inside the published document or selected subtree; publishing never follows a chart reference back into unselected corpus content.

Distributed OpenOrg builds include OpenOrg's registered Google OAuth client, so normal setup is one click on *Connect Google Drive* followed by consent in the system browser. Users do not create a Google Cloud project or import credentials. *Use a custom OAuth client* remains available as an advanced option for self-built or separately branded deployments; it accepts the JSON for a client of type *Desktop app*, not Web application. OpenOrg masks the paired client secret and stores it only with the resulting OAuth credential in macOS Keychain. Google passwords and OAuth tokens are never pasted into OpenOrg. See [[https://developers.google.com/identity/protocols/oauth2/native-app][Google's desktop OAuth guide]], [[https://developers.google.com/identity/protocols/oauth2][Google's OAuth overview]], and [[https://developers.google.com/workspace/drive/api/guides/api-specific-auth][Drive scope guidance]].

Property drawers, TODO state, tags, planning and clock data, comments, commented subtrees, dynamic blocks, table formulas, raw HTML, internal IDs, unresolved local links, and runtime data are removed before either destination receives content. Referenced supported raster images are embedded in the sealed artifact.

* Agent work and approvals

#+begin_export html
<figure class="org2-section-shot"><img src="assets/screenshots/macos-workspace-runs-review.png" alt="OpenOrg Agent Work showing a delegated result ready for review" loading="lazy" /><figcaption>Review the result, evidence, and proposed action in one place.</figcaption></figure>

Agent Work keeps each delegated job together with its goal, context, progress, outputs, citations, checks, and final outcome. The *Runs* view shows what is active, blocked, complete, or failed. The *Review* view collects the specific decisions that require a person.

You can approve, reject, request changes, discuss, or record that work was completed elsewhere. Batch selection applies independent decisions concurrently, coalesces the visible queue update and reconciliation, and still serializes writes that target the same canonical run or source file. Review material stays inspectable after a decision, providing a durable record of what was proposed and what happened.

The *Automations* view turns a prompt, optional agent profile, schedule, and any enabled AI destination into an ordinary file under =workflows/=. OpenOrg checks schedules while it is running, creates a durable run before dispatch, catches up the latest missed occurrence after sleep or relaunch, prevents overlapping attempts, and keeps one destination-neutral history. The toolbar and row menu can delete a selected definition after confirmation without deleting its prior run history. Fuller reusable workflows use the same files and add inputs, steps, validation, outputs, and approval boundaries. See [[file:workflows.org][Automations and workflows]] for the full lifecycle.

* AI chat and agents

#+begin_export html
<figure class="org2-section-shot"><img src="assets/screenshots/macos-workspace-ai-room.png" alt="OpenOrg shared AI room with independently attributed agent responses" loading="lazy" /><figcaption>Ask one destination or compare several in a shared room.</figcaption></figure>
#+end_export

AI is optional. OpenOrg does not require an OpenOrg account, and ordinary note, Agenda, search, meeting, and document features work without an AI destination.

In *OpenOrg → Settings… → AI Chat*, you can configure named destinations including local Codex, local Claude Code, remote Codex App Server, OpenClaw, OpenAI-compatible providers, Anthropic, OpenRouter, or Ollama. API keys are stored in macOS Keychain, not in the corpus.

The chat header’s *AI Chat Settings…* button opens this settings pane directly. Model, destination, and reasoning controls remain available in narrow chat panes: secondary labels collapse to icons, and very narrow panes put the controls above the send actions. Shared rooms use a compact *Models* menu for their per-destination choices. To configure the built-in OpenClaw gateway, choose *Edit* beside its destination in Settings, then *Configure Gateway…*; gateway connection and pairing controls appear only in that editor. Brief and inactive-thread preferences live in the shared *Conversations* section.

Direct providers have an opt-in *Workspace tools (experimental)* setting. It runs a small TypeScript executor using the Node runtime already shipped inside OpenOrg; no separate agent harness or Node installation is required. The executor can search the active corpus, read effective file text (including unsaved editor drafts), and propose whole-file edits. Every apply request opens a native review of the original and proposed text. Cancel declines edits for the rest of that turn. OpenOrg binds tools to the originating turn and authorized corpora, and rechecks the exact preview's hashes before writing.

This prototype supports text conversations with tool-capable OpenAI-compatible, Anthropic, OpenRouter, and Ollama models; support for an endpoint does not guarantee that every model can use tools reliably. Configure a model and endpoint in the destination, enable workspace tools, then try asking for a cited answer and a small task edit in a disposable corpus. Cloud credentials use the existing Keychain configuration. Local Ollama requires a separately running server and an installed model.

Only one bundled turn runs at a time. Replies arrive after each model step, with tool progress between steps; token streaming, automatic context compaction, restart recovery of an in-flight tool loop, attachments, general shell/browser access, and unattended edit approval are outside this prototype. Stop terminates the helper; the existing chat history and successfully applied file changes remain in OpenOrg. Each turn has a 12-step limit, a 48-tool-call limit, a 4 MiB context/response limit, and a two-minute timeout per model request. Workspace tools are disabled by default, preserving context-only chat for existing destinations.

To use Claude Code, install it and sign in with =claude auth login=, then enable *Claude Code* in AI Chat settings. OpenOrg starts the local CLI, streams its replies, and resumes the same Claude Code session on later turns. No Anthropic key is copied into OpenOrg. The Local Agent Permissions setting maps to Claude Code's Plan, Accept Edits, or Bypass Permissions mode.

Add files, headings, selected items, images, PDFs, audio, or other supported attachments as explicit context. Typing =@= finds corpus files and destinations. Chat text has one selection region across the bounded visible transcript, so a drag can copy across paragraphs, bullets, and consecutive messages without mounting an unbounded history. Selection highlights use the same glyph layout as the displayed text, including inside agent rounds. Copying a table, either by selecting its cells or using the message’s Copy button, supplies a styled HTML table for rich-text destinations such as email and an aligned Org table for plain-text editors. In a shared room, mention a destination by name or use =@all=; every reply remains attributed to the agent that produced it.

Agents can display images directly in their replies with an Org image link on its own line, such as =[[file:/absolute/path/qr.png][QR code]]= or =[[https://example.com/chart.png][Chart]]=. Image-only replies and images alongside prose both render inline, including in agent rounds. Relative paths resolve against the active local corpus. Local files must be accessible on the Mac; files generated on an SSH host must first be retrieved or synchronized to a local path. OpenOrg includes this guidance in the agent’s context. Tool output and opening another application do not by themselves attach an image to the conversation.

*Pass to Agent* menus list active portable agent profiles from the corpus. Choosing one writes its readable name as =ASSIGNEE= and preserves its stable =AGENT_REF= plus primary =GOAL_REF= when available; the configured legacy handoff target remains available as a fallback.

Threads and their context are stored locally with the corpus. Hover a sidebar thread to reveal its Settle action; settled threads show Reopen instead. The action keeps its space in narrow sidebars so hovering does not shift the title. Long-running OpenClaw turns can stream progress, be stopped, and reconnect after an app restart when the connected runtime supports it.

The iOS app can relay Codex, Claude Code, and other configured chat destinations to a paired Mac over Tailscale. The selected host remains responsible for corpus access and model connections. A [[file:headless-server.org][headless OpenOrg server]] on another Mac can keep chats and scheduled automations available while the laptop is away. See [[file:getting-started.org::*iOS app][iOS setup]] for the current beta and pairing path.

See [[file:agent-quickstart.org][Agent quickstart]] for permissions, runtime integration, durable runs, and automation details.

Meetings can be recorded in OpenOrg or created from an existing audio file. Choose local Whisper, macOS Speech, Fluid Voice, or a custom local command for transcription. The resulting audio, transcript, metadata, and notes remain visible in the corpus. A freshly transcribed meeting can optionally be sent to a named AI destination for a summary or follow-up workflow.

The *Sources* view manages supported Slack and Notion connections. Each connector can run on demand, pause or resume its schedule, and use a repeating interval or daily time. Imported material is staged for review rather than silently promoted into your canonical notes, and credentials remain outside the corpus.

* Privacy and security

Your corpus is an ordinary folder on your Mac. OpenOrg does not upload it to an OpenOrg service. Information leaves the Mac only when you use a destination or source provider you configured, so its retention and data-use policy still applies.

Secrets belong in macOS Keychain or another protected local store. OpenOrg also supports GPG-backed =:crypt:= subtrees when individual sections need encrypted storage. Consequential external actions can be held for explicit approval before execution.

Back up or sync the corpus with a file-oriented tool you understand, such as Git, Time Machine, iCloud Drive, or Syncthing.

* Keyboard essentials

- =Cmd-1= through =Cmd-6= open the main workspace surfaces.
- =Cmd-P= or =Cmd-K= opens Quick Open.
- =Cmd-Ctrl-Return= opens global capture.
- =Cmd-7=, =Cmd-8=, and =Cmd-9= open today's, yesterday's, and tomorrow's daily notes. Choose *Daily → Choose Date…* or press =Cmd-Shift-7= to open or create the daily note for any date.
- =Cmd-A= selects visible items in Agenda, Files, Runs, or Review; =Shift-Up/Down= extends the selection.
- =Cmd-F= searches the active pane.
- =Cmd-R= refreshes the workspace when you need a manual reconciliation.
- =Cmd-T= opens a tab; =Cmd-Shift-[= and =Cmd-Shift-]= move between tabs.

Use the in-app keyboard shortcuts sheet for the complete map.

* Install and troubleshoot

Download the signed and notarized app from [[file:downloads.org][Downloads]]. Developers who want to build OpenOrg from source can follow the repository instructions on [[https://github.com/aviaviavi/org2][GitHub]].

OpenOrg checks for signed updates when it opens and every two hours by default. Use *OpenOrg → Check for Updates…* to check manually, or the *Updates* settings to turn automatic checks off and choose whether downloads should install when you quit. Update prompts can also remind you later or skip a version.

Quitting during active chats, recording, or meeting processing asks for confirmation. OpenOrg makes a best-effort save for up to five seconds after you confirm. A second Quit request (including =Cmd-Q= or AppleScript) bypasses the pending confirmation or save and exits immediately; unsaved changes or recent output may be lost. If an ordinary quit cannot finish saving, a visible dialog offers Quit or Keep Open; slow saves offer Quit or Keep Waiting. Developer =--restart= builds send a second quit request after five seconds if needed, and only replace the bundle after the app exits.

For a reproducible launch or refresh problem, use the [[file:macos-diagnostics.org][macOS diagnostics guide]]. Sanitize diagnostics before sharing them, and never include credentials or private corpus content.

* Custom TODO states and action feedback

Open Settings → Workspace → TODO States to edit corpus-wide defaults. Enter space-separated names in the Active states and Terminal states fields. Add independent sequences as needed, then choose Save TODO States. Use Built-in States clears the custom rows; Save applies that choice. Validation errors stay beside the fields, and stale settings require a reload before saving. The settings are portable corpus configuration, shared by the CLI and other clients.

A file can override these defaults. Add a declaration such as =#+TODO: TODO MISSED | DONE SKIPPED= to a file. States before =|= remain active; those after it are terminal. OpenOrg’s heading editor includes the declared keywords, and heading buttons use the configured active/terminal states. Marking a custom state DONE replaces its keyword, preserves the title and ID, and maintains CLOSED metadata.

Workspace errors appear in a dismissible banner on the current surface, with selectable details. Failed actions no longer depend on a hidden status message; successful actions do not open confirmation dialogs.
