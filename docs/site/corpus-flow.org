#+TITLE: Corpus flow
#+SUBTITLE: Canonical zones for Celorga knowledge corpora

Celorga treats a corpus like a small local knowledge compiler. Source material moves through explicit zones so humans and tools can tell which files are authored, which files are derived, and which boundaries need provenance.

The canonical flow is:

#+begin_src text
raw/ -> notes/ -> compiled/ -> views/ -> publish/
#+end_src

Start with the zones your corpus needs. Once a corpus adopts these names, Celorga lint can check the trust boundary without relying on convention alone.

* Zones

| Directory | Role | Canonical? | Purpose |
|---+---+---+---|
| =raw/= | =raw= | source evidence | Inbox material, imports, captures, transcripts, clippings, and other minimally edited inputs. |
| =notes/= | =canonical= | yes | Human-authored durable notes, tasks, decisions, IDs, links, and properties. This is the primary corpus. |
| =compiled/= | =compiled= | generated | Normalized or aggregated machine outputs derived from raw/canonical inputs. |
| =views/= | =view= | generated | Query results, indexes, dashboards, agenda snapshots, graph views, or other read models. |
| =publish/= | =report= | generated/public-facing | Exported reports, sites, feeds, handoff documents, or other presentation outputs. |

Canonical authorship lives in =notes/=. Generated outputs may be useful and may be committed, but they should be reproducible from provenance whenever possible.

Long-running account workflows follow the same boundary. For example, an account file under =notes/account-outreach/accounts/= contains reviewed identity, aliases, commercial context, and durable work history because those facts are curated canonical knowledge. Imported CRM rows, email/provider responses, and collector payloads belong under =raw/account-outreach/=; generated rankings and next-account selections belong under =views/account-outreach/=. The account ledger links those sources and native run approvals rather than copying raw payloads or creating a second approval authority.

* Trust boundaries

The most important boundary is between canonical material and generated material:

- =raw/= can be messy and externally sourced; preserve it when evidence matters.
- =notes/= is the reviewed human source of truth.
- =compiled/=, =views/=, and =publish/= are derived outputs and should say where they came from.
- Generated outputs should not silently become canonical notes. Promote useful generated text by copying or rewriting it into =notes/= and reviewing it there.

* Artifact metadata

Use file-level or headline-level property drawers to declare artifact roles and provenance.

Canonical note example:

#+begin_src org
:PROPERTIES:
:ID: project-alpha
:CELORGA_ARTIFACT_ROLE: canonical
:END:
#+end_src

Generated view example:

#+begin_src org
:PROPERTIES:
:ID: project-alpha-dashboard
:CELORGA_ARTIFACT_ROLE: view
:CELORGA_PROVENANCE: id:project-alpha, query:todo-status-open
:CELORGA_GENERATOR: celorga query --format org
:CELORGA_GENERATED_AT: 2026-05-10T22:30:00Z
:CELORGA_SOURCE_HASHES: file:notes/project-alpha.org=sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
:CELORGA_REVIEW_STATUS: review-required
:END:
#+end_src

The standard generated-artifact property set is:

- =CELORGA_ARTIFACT_ROLE= records the trust boundary: =raw=, =canonical=, =compiled=, =view=, or =report=.
- =CELORGA_PROVENANCE= records source references as =kind:value= tokens.
- =CELORGA_GENERATOR= records the deterministic command, job, or workflow that produced the artifact.
- =CELORGA_GENERATED_AT= records an ISO date or timestamp for the generation run.
- =CELORGA_SOURCE_HASHES= optionally records content hashes for specific inputs as ~kind:value=sha256:<64 hex chars>~.
- =CELORGA_REVIEW_STATUS= records whether generated content is =generated=, =review-required=, =reviewed=, or =promoted=.

The supported =CELORGA_ARTIFACT_ROLE= values are:

- =raw=
- =canonical=
- =compiled=
- =view=
- =report=

The conventional directory mapping is:

- =raw/= -> =raw=
- =notes/= -> =canonical=
- =compiled/= -> =compiled=
- =views/= -> =view=
- =publish/= -> =report=

=CELORGA_PROVENANCE= entries use =kind:value= tokens separated by commas or semicolons. Supported kinds are =id=, =file=, =query=, =run=, =url=, =note=, and =artifact=. =CELORGA_SOURCE_HASHES= uses the same source kinds plus a SHA-256 digest, for example ~file:notes/project-alpha.org=sha256:...~.

* Lint workflow

Run lint over the corpus root:

#+begin_src sh
celorga lint --dir /path/to/corpus --recursive
#+end_src

When files live under the conventional directories, lint checks that their declared =CELORGA_ARTIFACT_ROLE= matches the path. It also checks generated artifacts for provenance, generator metadata, generated timestamps, source-hash syntax, review-status values, duplicate IDs, and unresolved provenance references.

A minimal corpus can start like this:

#+begin_src text
corpus/
  raw/
  notes/
  compiled/
  views/
  publish/
#+end_src

Then wire editor, query, export, and publish commands to read from =notes/=. Write derived results into =compiled/=, =views/=, or =publish/=, leaving canonical notes unchanged.
